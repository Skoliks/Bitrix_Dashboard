# UI/UX brief: дашборд воронки продаж Битрикс24

## 1. Контекст и цель интерфейса

Приложение встраивается в Битрикс24 как iframe-пункт левого меню и показывает руководителю отдела продаж агрегированную аналитику по сделкам CRM. MVP работает только на чтение: пользователь не создаёт, не изменяет и не удаляет сделки.

Главная UX-цель — дать руководителю быстрый ответ на вопросы:

- сколько сделок открыто сейчас;
- сколько сделок было создано и выиграно за период;
- какая сумма выигранных сделок и средний чек;
- как распределены сделки по стадиям выбранной воронки;
- как менялась динамика созданных и выигранных сделок;
- какие сделки были созданы последними и кто за них отвечает.

Интерфейс должен быть рабочим и плотным, без маркетинговых экранов, декоративных hero-блоков и лишних объяснений. Основной сценарий — регулярный просмотр показателей внутри CRM, поэтому важны сканируемость, предсказуемые фильтры, ясные предупреждения и устойчивое поведение при неполных данных.

## 2. Пользователи и сценарии

### 2.1. Основной пользователь

Руководитель отдела продаж или пользователь с CRM-доступом к сделкам. Дашборд показывает только те данные, которые доступны текущему пользователю по правам Битрикс24.

### 2.2. Основные сценарии

1. Открыть приложение из левого меню Битрикс24.
2. Увидеть дашборд с настройками по умолчанию: основная доступная воронка, последние 30 календарных дней, «Все валюты».
3. Сменить воронку, период или валюту.
4. Сравнить KPI, воронку по стадиям и график динамики.
5. Просмотреть последние созданные сделки.
6. Открыть карточку сделки в Битрикс24 по клику на строку таблицы, если доступна корректная ссылка или SDK-действие.
7. Понять, когда данные неполные: усечённая агрегация, отсутствующая валюта, недоступные пользователи, неизвестная семантика стадий.

### 2.3. Неосновные сценарии MVP

В MVP не проектируются отдельные экраны для режима «Все воронки», фильтра по ответственному, фильтра по отделу, админского режима, редактирования сделок и истории переходов между стадиями.

## 3. Информационная архитектура

MVP состоит из одного основного экрана дашборда и системных состояний внутри него. Отдельная внутренняя навигация не нужна: приложение уже открывается из навигации Битрикс24.

Структура экрана сверху вниз:

1. Заголовок и краткий контекст выбранных данных.
2. Панель фильтров: воронка, период, валюта.
3. Зона предупреждений, если есть warnings.
4. KPI-карточки.
5. Аналитическая зона: воронка по стадиям и график динамики.
6. Таблица последних созданных сделок.

На широких экранах воронка и график могут располагаться в две колонки. В узком iframe или на мобильной ширине блоки идут одной колонкой в том же порядке.

## 4. Экраны

### 4.1. Экран загрузки приложения

Показывается после открытия iframe, пока frontend инициализирует контекст Битрикс24 и запрашивает bootstrap-данные у BFF.

Содержимое:

- компактный заголовок «Дашборд продаж»;
- skeleton для панели фильтров;
- skeleton для KPI-карточек;
- skeleton для графика, воронки и таблицы.

Поведение:

- не показывать пустые нули до завершения первой загрузки;
- если bootstrap завершился ошибкой авторизации или доступа, перейти в соответствующее ошибочное состояние;
- если справочник пользователей недоступен, не блокировать весь дашборд, а показать предупреждение после загрузки данных.

### 4.2. Основной экран дашборда

Главный рабочий экран для просмотра аналитики.

Состав:

- заголовок «Дашборд воронки продаж»;
- вторичная строка с названием выбранной воронки, периодом и timezone портала, если он доступен;
- фильтр воронки;
- фильтр периода;
- фильтр валюты;
- предупреждения о качестве данных;
- KPI-карточки;
- визуализация воронки по стадиям;
- график динамики;
- таблица последних созданных сделок.

Дефолтное состояние:

- воронка: основная `categoryId = 0`, если доступна; иначе первая доступная воронка из справочника;
- период: последние 30 календарных дней, включая текущий день, в timezone портала;
- валюта: «Все валюты».

### 4.3. Выбор периода

Фильтр периода должен поддерживать:

- последние 7 дней;
- последние 30 дней;
- последние 90 дней;
- текущий месяц;
- прошлый месяц;
- произвольный диапазон дат.

UX-правила:

- быстрые периоды оформить как список в dropdown или segmented-like меню внутри picker;
- произвольный диапазон открывает календарный выбор начала и конца;
- при выборе произвольного диапазона кнопка применения активна только при валидных датах;
- период хранится как календарные даты, бизнес-границы периода считает BFF в timezone портала.

### 4.4. Таблица последних сделок

Показывает 10-20 последних созданных сделок, рекомендуемое значение — 15.

Колонки:

- название сделки;
- сумма и валюта;
- стадия;
- ответственный;
- дата создания.

Поведение:

- сортировка по умолчанию `createdAt desc`;
- строка кликабельна, если доступно открытие карточки сделки в Битрикс24;
- при недоступном `/v1/users` в колонке ответственного показывать `assignedById` и предупреждение над дашбордом;
- если сумма или валюта отсутствуют, в строке показывать мягкий fallback, а денежные суммы считать по правилам неполных финансовых данных.

## 5. Состояния экрана и компонентов

### 5.1. Initial loading

Использовать skeleton-загрузку, повторяющую будущую структуру экрана. Для KPI — прямоугольники с высотой карточек; для графика и воронки — крупные placeholders; для таблицы — skeleton-строки.

### 5.2. Refresh loading

При смене фильтров не очищать весь экран мгновенно. Старые данные можно оставить приглушёнными, а в зоне изменяемых блоков показать loading overlay или inline spinner.

Правила:

- фильтры остаются доступными, если нет активного запроса, который может конфликтовать с новым выбором;
- если пользователь быстро меняет фильтры, показывать только результат последнего запроса;
- не смешивать данные разных наборов фильтров.

### 5.3. Empty dashboard

Показывается, когда по выбранной воронке, периоду и валюте нет сделок для аналитических блоков.

Содержимое:

- краткий заголовок: «Нет сделок за выбранный период»;
- пояснение: «Измените период, валюту или воронку, чтобы проверить другие данные»;
- основные действия: изменить период, сбросить валюту на «Все валюты».

KPI в этом состоянии могут показывать нули, если расчёт корректно выполнен. Воронка должна сохранять список стадий с нулевыми значениями, если справочник стадий доступен.

### 5.4. Empty reference data

Если нет доступных воронок, дашборд не может быть построен.

Содержимое:

- заголовок: «Нет доступных воронок»;
- текст: «Приложение не получило доступные воронки сделок для текущего пользователя»;
- действие: «Обновить»;
- подсказка для администратора: проверить CRM-права и scope `crm`.

### 5.5. Partial data warnings

Предупреждения не должны блокировать просмотр данных, если расчёт возможен.

Типы предупреждений:

- `DATA_TRUNCATED`: выборка больше 5000 сделок, агрегированные показатели могут быть предварительными;
- `INCOMPLETE_FINANCIAL_DATA`: часть сделок не имеет суммы или валюты, такие сделки учитываются в количестве, но исключаются из денежных сумм;
- `USERS_UNAVAILABLE`: имена ответственных недоступны, вместо них показываются ID;
- `UNKNOWN_STAGE_SEMANTICS`: часть показателей может быть рассчитана неполно, потому что семантика стадий недоступна;
- `MULTI_CURRENCY`: суммы показаны отдельно по валютам, без конвертации и объединения.

Визуально warnings показываются компактными alert-блоками под фильтрами. Если предупреждений несколько, их можно объединить в один блок со списком.

### 5.6. Access denied

Показывается при ошибках доступа к CRM-данным, стадиям, воронкам или необходимым scopes.

Содержимое:

- заголовок: «Недостаточно прав для просмотра дашборда»;
- пояснение с указанием недоступной части данных, если BFF вернул деталь;
- действие: «Обновить»;
- рекомендация: обратиться к администратору Битрикс24 и проверить scopes `crm` и `user`.

### 5.7. Session expired

Показывается при `TOKEN_MISSING`, `INVALID_SESSION`, `AUTH_REQUIRED`, `SESSION_EXPIRED` и аналогичных ошибках.

Содержимое:

- заголовок: «Сессия истекла»;
- пояснение: «Переоткройте приложение в Битрикс24, чтобы продолжить»;
- действие: «Обновить» или «Переоткрыть приложение», если placement/SDK позволяет.

### 5.8. Network, timeout, rate limit

Ошибки сети, таймауты и лимиты показываются как recoverable-состояния.

Содержимое:

- заголовок: «Не удалось загрузить данные»;
- короткая причина, если известна: таймаут, сервис временно недоступен, превышен лимит запросов;
- действие: «Повторить»;
- при rate limit можно показать нейтральный текст «Попробуйте повторить позже».

### 5.9. Validation error

Если BFF не смог сопоставить внешний контракт VibeCode API с внутренними DTO, UI показывает технически аккуратную ошибку без CRM-данных.

Содержимое:

- заголовок: «Данные пришли в неожиданном формате»;
- текст: «Дашборд не может корректно построить показатели. Передайте код ошибки разработчику»;
- технический код ошибки, request id или trace id, если доступен.

## 6. Основные действия пользователя

### 6.1. Сменить воронку

Пользователь выбирает одну доступную воронку из списка. После выбора дашборд перезагружает KPI, воронку, график и таблицу.

Правила:

- режим «Все воронки» не показывать в MVP;
- если выбранная ранее воронка стала недоступна, выбрать дефолтную доступную и показать предупреждение;
- стадии всегда соответствуют выбранной воронке.

### 6.2. Сменить период

Пользователь выбирает preset или произвольный диапазон. После применения периода обновляются все блоки.

Правила:

- созданные сделки считаются по `createdAt`;
- выигранные сделки считаются по `closedAt` и успешной семантике;
- таблица и воронка используют сделки с `createdAt` внутри периода;
- график группируется по дням до 31 дня, по неделям от 32 до 180 дней, по месяцам для более длинных периодов.

### 6.3. Сменить валюту

Пользователь выбирает конкретную валюту или «Все валюты».

Правила:

- в режиме «Все валюты» суммы разных валют не объединяются;
- денежные значения показываются отдельными строками по валютам;
- количественные метрики можно суммировать независимо от валюты;
- автоматической конвертации валют нет.

### 6.4. Открыть сделку

Пользователь кликает по строке таблицы. Если ссылка или SDK-действие доступно, открыть карточку сделки в Битрикс24.

Правила:

- клик по строке не должен выглядеть как действие редактирования;
- если открыть карточку нельзя, строка не должна иметь hover-состояние ссылки;
- никакие write-операции не запускаются.

### 6.5. Обновить данные

Действие доступно в ошибочных состояниях и может быть доступно как иконка в заголовке дашборда.

Правила:

- обновление сохраняет текущие фильтры;
- при повторной ошибке показывается то же состояние с обновлённым временем попытки, если это полезно;
- кнопка блокируется на время запроса.

## 7. Навигация

Внутри MVP нет многостраничной навигации. Основной путь пользователя:

`Левое меню Битрикс24 -> Дашборд воронки продаж -> фильтры/просмотр -> карточка сделки в Битрикс24`

Навигационные правила:

- не добавлять собственный sidebar внутри iframe;
- не дублировать навигацию Битрикс24;
- заголовок приложения должен быть стабильным и заметным, но не занимать много вертикального пространства;
- внешнее действие открытия сделки должно использовать возможности Битрикс24 SDK или корректную ссылку.

## 8. Компоненты интерфейса

### 8.1. App shell

Отвечает за общий контейнер iframe, тему, локаль, глобальные ошибки и уведомления.

Требования:

- адаптироваться к ограниченной ширине iframe;
- не полагаться на полноэкранный desktop viewport;
- поддерживать dev/mock режим, но не показывать его обычному пользователю как отдельный продуктовый режим.

### 8.2. Header

Состав:

- название «Дашборд воронки продаж»;
- подстрока с выбранной воронкой и периодом;
- опциональная иконка обновления;
- опциональный timestamp последнего успешного обновления.

### 8.3. Filter bar

Компоненты:

- select воронки;
- period picker;
- select валюты.

Правила:

- фильтры должны помещаться в одну строку на широкой области;
- на узкой ширине переноситься в 2-3 строки без горизонтального скролла;
- длинные названия воронок обрезать с tooltip;
- состояние загрузки справочников показывать прямо в контролах.

### 8.4. KPI cards

Карточки:

- «Открыто сейчас»;
- «Открыто из созданных за период»;
- «Выиграно за период»;
- «Сумма выигранных за период»;
- «Средний чек выигранной сделки».

Содержимое карточки:

- короткий заголовок;
- основное значение;
- вторичное значение, если нужно показать сумму и количество;
- маркер валюты или список сумм по валютам;
- tooltip с правилом расчёта для неоднозначных KPI.

### 8.5. Funnel visualization

Показывает все стадии выбранной воронки в справочном порядке, включая нулевые стадии.

Для каждой стадии:

- название;
- количество сделок;
- доля от общей выборки;
- суммы по валютам;
- визуальная ширина или сегмент, отражающий относительный объём.

Правила:

- цвет стадии можно брать из справочника, если он доступен;
- если цвет недоступен, использовать системную палитру;
- нулевые стадии остаются видимыми, но визуально приглушёнными;
- не угадывать состояние стадии по названию.

### 8.6. Trend chart

Показывает две серии:

- созданные сделки;
- выигранные сделки.

Правила:

- ось X соответствует группировке периода;
- tooltip показывает дату/период, количество созданных и выигранных;
- пустые интервалы отображаются как нули;
- график не должен ломаться при одной точке данных.

### 8.7. Recent deals table

Таблица должна быть компактной и сканируемой.

Правила:

- sticky header можно использовать, если таблица получает внутренний скролл;
- на узкой ширине второстепенные колонки можно сжимать, но название сделки, стадия и дата должны оставаться читаемыми;
- суммы форматировать с кодом валюты или символом, если он доступен;
- строки без суммы показывать как «Сумма не указана» или компактный fallback.

### 8.8. Alerts and notifications

Используются для warnings и recoverable-ошибок.

Типы:

- info: нейтральные системные пояснения;
- warning: неполные данные;
- error: блокирующая ошибка;
- success в MVP не нужен как постоянный паттерн.

## 9. Пустые состояния

### 9.1. Нет сделок

Показывать, когда запрос успешен, но выборка пуста.

Текст:

- «Нет сделок за выбранный период»
- «Измените период, валюту или воронку, чтобы проверить другие данные»

Действия:

- изменить период;
- сбросить валюту на «Все валюты», если выбрана конкретная валюта.

### 9.2. Нет последних сделок

Может возникать отдельно от KPI, если таблица загружается отдельным запросом.

Текст:

- «Последних созданных сделок нет»
- «За выбранный период в этой воронке не найдено созданных сделок»

### 9.3. Нет стадий

Если справочник стадий выбранной воронки пуст или недоступен, блок воронки показывает ошибку компонента.

Текст:

- «Не удалось показать стадии воронки»
- «Справочник стадий недоступен для выбранной воронки»

## 10. Ошибки

### 10.1. Блокирующие ошибки

Блокируют весь дашборд:

- сессия отсутствует или истекла;
- нет доступа к сделкам или воронкам;
- bootstrap-данные не загрузились;
- BFF вернул критическую validation error.

### 10.2. Частичные ошибки

Не блокируют весь дашборд:

- недоступны имена пользователей;
- агрегированные данные усечены;
- часть сделок без валюты или суммы;
- неизвестна семантика части стадий, но часть данных можно показать;
- таблица последних сделок не загрузилась при успешных KPI.

### 10.3. Тон сообщений

Сообщения должны быть конкретными и без обвинения пользователя. Хороший формат:

- что произошло;
- какая часть данных затронута;
- что можно сделать.

Не показывать пользователю raw stack traces, токены, полные URL с секретами, названия внутренних переменных окружения и полные CRM-ответы.

## 11. Дизайн-система

### 11.1. Общий стиль

Интерфейс должен выглядеть как рабочий аналитический инструмент внутри Битрикс24:

- спокойная светлая тема по умолчанию;
- плотная сетка;
- минимум декоративных элементов;
- нейтральные поверхности;
- акцентные цвета только для действий, статусов и графиков;
- визуальное соответствие Bitrix24 UI, если библиотека доступна.

### 11.2. Сетка и layout

Рекомендуемая сетка:

- page padding: 16-24 px в зависимости от ширины iframe;
- gap между крупными секциями: 16 px;
- gap внутри панелей: 8-12 px;
- KPI-сетка: 5 карточек в строку на широких экранах, 2-3 на средней ширине, 1 на узкой;
- аналитическая зона: 2 колонки на широких экранах, 1 колонка на узких.

Карточки использовать для KPI, отдельных аналитических блоков и таблицы. Не вкладывать карточки в карточки.

### 11.3. Типографика

Принципы:

- системный шрифт Битрикс24 или стандартный sans-serif;
- крупное число KPI должно быть самым заметным элементом карточки;
- заголовки блоков компактные;
- длинные названия сделок и воронок обрезать с tooltip;
- не использовать отрицательный letter-spacing.

Рекомендуемые размеры:

- заголовок страницы: 20-24 px;
- заголовки блоков: 14-16 px;
- KPI value: 24-32 px;
- основной текст и таблица: 13-14 px;
- подписи и metadata: 12-13 px.

### 11.4. Цвета

Роли цветов:

- background: основной фон приложения;
- surface: фон карточек и таблиц;
- border: разделители;
- text primary: основные значения;
- text secondary: подписи;
- accent: основные interactive-состояния;
- success: выигранные сделки;
- warning: неполные данные;
- danger: ошибки доступа и критические ошибки;
- chart created: созданные сделки;
- chart won: выигранные сделки.

Не строить весь UI на одной цветовой семье. Палитра должна быть нейтральной с несколькими функциональными акцентами.

### 11.5. Компоненты и controls

Использовать привычные controls:

- select для воронки и валюты;
- date range picker для произвольного периода;
- dropdown/menu для presets периода;
- icon button для обновления;
- table для последних сделок;
- tooltip для правил расчёта и сокращённых названий;
- alert для предупреждений;
- skeleton для загрузки.

Если доступны Bitrix24 UI и Bitrix24 icons, использовать их как базовый источник визуального языка.

### 11.6. Иконки

Иконки нужны только там, где они ускоряют распознавание:

- обновить;
- предупреждение;
- ошибка;
- открыть сделку;
- календарь;
- фильтр/воронка;
- валюта.

Иконки не должны заменять критически важный текст в предупреждениях и ошибках.

### 11.7. Форматирование данных

Даты:

- показывать в формате, привычном для локали портала;
- период считать в timezone портала;
- в таблице можно показывать дату и короткое время, если это полезно.

Деньги:

- не объединять разные валюты;
- в режиме «Все валюты» показывать суммы списком по валютам;
- если символ валюты неизвестен, показывать код валюты;
- сделки без валюты исключать из денежных сумм и отмечать warning.

Количество:

- использовать разделители тысяч;
- нули показывать явно, а не скрывать блок.

### 11.8. Адаптивность

Приложение должно корректно работать внутри iframe разной ширины.

Минимальные правила:

- без горизонтального скролла страницы;
- фильтры переносятся строками;
- KPI-карточки переходят в 1 колонку на узкой ширине;
- график и воронка сохраняют читаемые подписи;
- таблица может иметь горизонтальный скролл внутри себя, если иначе потеряется читаемость колонок.

### 11.9. Доступность

Требования:

- все controls доступны с клавиатуры;
- фокус видим;
- alerts объявляются как значимые состояния;
- цвет не является единственным способом передать warning/error;
- таблица имеет корректные заголовки колонок;
- график имеет текстовую альтернативу через tooltip/summary.

## 12. UX-ограничения MVP

- Не показывать режим «Все воронки».
- Не добавлять фильтр по ответственному и отделу.
- Не показывать админский режим с `vibe_api_...`.
- Не давать пользователю действий записи в CRM.
- Не обещать точность агрегатов при `meta.truncated=true`.
- Не конвертировать валюты автоматически.
- Не угадывать статус сделки по названию стадии.
- Не скрывать доступные данные из-за частичных warnings, если расчёт возможен.

## 13. Acceptance checklist для UI

- Приложение открывается из левого меню Битрикс24 и показывает основной дашборд.
- Дефолтные фильтры: доступная основная воронка, последние 30 дней, «Все валюты».
- Пользователь может сменить воронку, период и валюту.
- KPI, воронка, график и таблица обновляются по активным фильтрам.
- Воронка показывает все стадии выбранной воронки, включая нулевые.
- График показывает созданные и выигранные сделки с корректной группировкой периода.
- Таблица показывает последние созданные сделки и fallback на `assignedById`.
- Пустые состояния понятны и предлагают релевантное действие.
- Ошибки доступа, сессии, сети и validation error различаются текстом и действиями.
- Warnings о неполных данных видимы, но не блокируют просмотр корректно рассчитанных данных.
- UI не содержит секретов, токенов, raw stack traces и полных CRM-ответов.
- Интерфейс остаётся читаемым в iframe на широкой, средней и узкой ширине.
