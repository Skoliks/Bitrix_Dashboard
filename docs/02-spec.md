# Техническая спецификация: дашборд воронки продаж Битрикс24

## 1. Назначение и границы

Документ описывает техническое устройство MVP приложения «Дашборд воронки продаж». Приложение встраивается в левое меню Битрикс24 и показывает руководителю отдела продаж агрегированную аналитику по сделкам CRM через VibeCode API.

MVP является read-only приложением: оно не создаёт, не изменяет и не удаляет сделки CRM. Все данные отображаются в рамках CRM-прав пользователя, который открыл приложение в Битрикс24.

В MVP входят:

- встраивание в Битрикс24 как iframe-приложение;
- авторизация через `vibe_app_...` и пользовательскую сессию;
- Backend for Frontend (BFF) между frontend и VibeCode API;
- выбор одной воронки сделок;
- выбор периода анализа;
- фильтр валюты, включая режим «Все валюты»;
- KPI, воронка по стадиям, график динамики, таблица последних созданных сделок;
- состояния загрузки, ошибок, пустых данных и предупреждений.

В MVP не входят:

- режим «Все воронки»;
- фильтры по ответственному сотруднику и отделу;
- собственная ролевая модель поверх CRM-прав Битрикс24;
- анализ истории переходов между стадиями;
- автоматическая конвертация валют;
- расчёт по товарным позициям, оплатам, счетам, налогам и пользовательским финансовым полям;
- любые операции записи в CRM.

## 2. Архитектура

### 2.1. Общая схема

Целевая цепочка вызовов:

`Битрикс24 iframe -> Vue frontend -> Node.js BFF в Black Hole -> VibeCode API -> Bitrix24 CRM`

Компоненты:

- **Frontend**: Vue 3 + Vite приложение, встроенное в iframe Битрикс24. Отвечает за UI, фильтры, отображение метрик, графиков, таблиц и пользовательских состояний.
- **VibeCode Gateway**: передаёт приложению контекст запуска и пользовательскую сессию согласно модели встроенного приложения.
- **BFF приложения**: серверный слой на Node.js 20, размещённый в Black Hole. Хранит `vibe_app_...`, принимает запросы frontend, извлекает пользовательский контекст, вызывает VibeCode API, нормализует ответы и возвращает frontend безопасные DTO.
- **VibeCode API**: источник CRM-данных, справочников, пользователей, валют и агрегированных расчётов.
- **Битрикс24 CRM**: конечный источник прав доступа и бизнес-данных.

### 2.2. Принципы архитектуры

- Frontend не содержит `vibe_app_...`, `vibe_api_...` или пользовательский session token.
- BFF является единственной точкой доступа frontend к CRM-данным.
- BFF не обходит CRM-права пользователя и выполняет запросы к VibeCode API в пользовательском контексте.
- Сервисный ключ `vibe_api_...` допускается только для разработки, диагностики, smoke-тестов и явно отделённых админских сценариев вне пользовательского MVP.
- Внутренние модели приложения должны быть стабильными; отличия фактического контракта VibeCode API закрываются Zod-схемами внешних ответов и явным маппингом в BFF.
- Справочники кэшируются краткосрочно на стороне BFF, а пользовательские агрегаты считаются с учётом активных фильтров и прав текущего пользователя.
- Интеграционный слой нельзя реализовывать по предполагаемым именам полей. Перед ним нужны redacted fixtures реальных API-ответов и contract-тесты.

### 2.3. Рекомендуемый стек

Frontend:

- Vue 3;
- Vite;
- TypeScript;
- Bitrix24 UI / Bitrix24 icons;
- `@bitrix24/b24jssdk` для lifecycle iframe, локализации, открытия карточки сделки и вспомогательных сценариев Битрикс24;
- TanStack Table для таблицы последних сделок;
- Unovis для графиков;
- собственный Vue/SVG-компонент для воронки по стадиям;
- `@internationalized/date` для календарных дат и выбора периода;
- `date-fns` для форматирования дат;
- Zod для проверки DTO на границах API;
- Vitest для unit-тестов.

BFF:

- Node.js 20;
- TypeScript;
- HTTP API с JSON-контрактами;
- хранение секретов в переменных окружения или секрет-хранилище сервера;
- серверный HTTP-клиент к VibeCode API;
- in-memory cache или внешний cache для справочников;
- структурированное логирование без токенов и персональных данных в явном виде.

Рекомендуемая модель деплоя:

- один репозиторий;
- один Black Hole deployment;
- BFF раздаёт собранный Vue frontend и обслуживает `/api/*`;
- обязательные инфраструктурные endpoint'ы: `GET /health`, `GET /ready`;
- проверка env при старте, structured logs, graceful shutdown, версия deployment и централизованный error handler.

## 3. Модули

### 3.1. Frontend-модули

**App shell**

- инициализация iframe-приложения;
- определение режима запуска: внутри Битрикс24 или локальный mock/dev режим;
- глобальные состояния: тема, локаль, ошибки, уведомления.

**Dashboard page**

- компоновка страницы;
- управление активными фильтрами;
- запуск загрузки данных;
- распределение данных по KPI, funnel chart, trend chart и table.

**Filters**

- выбор воронки;
- выбор периода: последние 7 дней, последние 30 дней, последние 90 дней, текущий месяц, прошлый месяц, произвольный диапазон;
- выбор валюты: конкретная валюта или «Все валюты».

**KPI cards**

- «Открыто сейчас»;
- «Открыто из созданных за период»;
- «Выиграно за период»;
- «Сумма выигранных за период»;
- «Средний чек выигранной сделки».

**Funnel visualization**

- отображение всех стадий выбранной воронки в справочном порядке;
- количество сделок, доля от выборки, суммы по валютам;
- нулевые стадии остаются видимыми.
- реализация через собственный Vue/SVG-компонент без отдельной тяжёлой библиотеки.

**Trend chart**

- линия созданных сделок по `createdAt`;
- линия выигранных сделок по `closedAt` и успешной семантике;
- группировка по дням, неделям или месяцам в зависимости от длины периода.

**Recent deals table**

- 10-20 последних созданных сделок, рекомендуемо 15;
- сортировка `createdAt desc`;
- отображение названия, суммы, валюты, стадии, ответственного и даты создания;
- fallback на `assignedById`, если недоступен справочник пользователей.

**State and warning components**

- loading;
- empty state;
- access denied;
- expired session;
- partial aggregation warning;
- incomplete financial data warning;
- missing users scope warning;
- unknown stage semantics warning.

### 3.2. BFF-модули

**Session/context module**

- получает пользовательский контекст от VibeCode Gateway;
- валидирует наличие session token;
- не отдаёт session token в браузер;
- формирует авторизационные заголовки для VibeCode API.

**VibeCode client**

- добавляет `X-Api-Key: <VIBECODE_APP_KEY>`;
- добавляет `Authorization: Bearer <USER_SESSION_TOKEN>`;
- выполняет запросы к `/v1/*`;
- нормализует ошибки сети, доступа, лимитов и сессии.

**Reference data service**

- загружает и кэширует воронки, стадии, пользователей и валюты;
- выбирает справочник стадий по `categoryId`;
- поддерживает fallback для отсутствующих users.
- использует cache key с учётом портала, например `stages:{portalId}:{categoryId}`.

**Deals query service**

- строит фильтры по воронке, периоду, валюте и семантике стадии;
- вызывает `/v1/deals/aggregate` для быстрых агрегатов;
- вызывает `/v1/deals` или `/v1/deals/search` для таблицы последних сделок;
- проверяет `meta.truncated`.

**Aggregation service**

- приводит результаты API к внутренним метрикам;
- считает суммы отдельно по валютам;
- исключает сделки без валюты из денежных сумм, но оставляет их в количественных метриках;
- не угадывает состояние сделки по названию стадии.

**API DTO mapper**

- переводит внешний контракт VibeCode API во внутренние DTO frontend;
- изолирует frontend от переименований полей вроде `amount`/`opportunity` или `currency`/`currencyId`.
- валидирует внешние ответы через Zod-схемы, построенные по redacted fixtures реальных API-ответов.

**Date adapter**

- принимает календарные даты от UI;
- получает или использует timezone портала;
- формирует начало и конец периода в timezone портала;
- преобразует диапазон в однозначный ISO-формат с offset для VibeCode API;
- запрещает прямое использование `new Date('YYYY-MM-DD')` для бизнес-границ периода.

**Observability module**

- пишет технические логи запросов, кодов ошибок и длительности;
- маскирует ключи, токены, идентификаторы сессий;
- не логирует названия сделок, ФИО сотрудников, телефоны, email, полные CRM-ответы и суммы отдельных сделок;
- считает метрики отказов VibeCode API и частоты `meta.truncated=true`.

## 4. Данные

### 4.1. Основные сущности

**Deal**

- `id`: идентификатор сделки;
- `title`: название;
- `amount`: стандартная сумма сделки;
- `currency`: код валюты;
- `categoryId`: идентификатор воронки;
- `stageId`: идентификатор стадии;
- `stageSemanticId`: `P`, `S`, `F` или отсутствует;
- `assignedById`: ответственный;
- `createdAt`: дата создания;
- `updatedAt`: дата изменения;
- `closedAt`: дата закрытия.

**DealCategory**

- `id`: идентификатор воронки;
- `name`: название;
- `sort`: порядок, если доступен;
- `isDefault`: признак основной воронки, если доступен. Для основной воронки используется `categoryId = 0`.

**Stage**

- `id`: идентификатор стадии;
- `name`: название;
- `sort`: порядок;
- `color`: цвет, если доступен;
- `semantics`: `S`, `F` или `null`;
- `entityId`: `DEAL_STAGE` или `DEAL_STAGE_<categoryId>`.

**User**

- `id`: идентификатор пользователя;
- `name`: отображаемое имя;
- `avatar`: опционально;
- `active`: опционально.

**Currency**

- `code`: ISO-like код валюты;
- `name`: название;
- `symbol`: символ, если доступен;
- `format`: правила форматирования, если доступны.

**StageFunnelRow**

**TrendPoint**

**RecentDealRow**

- `id`;
- `title`;

- `stageName`;

- `assignedName`;

**Warning**

- `severity`;

### 4.3. Правила расчётов

Все расчёты применяют:

- CRM-права текущего пользователя;
- выбранную воронку;
- выбранный период, кроме KPI «Открыто сейчас»;
- выбранную валюту, если пользователь выбрал конкретную валюту.

Семантика сделки:

- основной источник: `deal.stageSemanticId`;
- fallback: `Stage.semantics` по `stageId`;
- если семантика неизвестна, приложение не классифицирует сделку по названию стадии и показывает предупреждение.

Периоды:

- UI хранит календарные даты без времени;
- BFF рассчитывает дату начала включительно и дату окончания включительно до конца дня в часовом поясе портала Битрикс24;
- BFF передаёт во внешний API готовый ISO-диапазон с offset;
- период по умолчанию: последние 30 календарных дней, включая сегодня.

Деньги:

- суммы разных валют не объединяются;
- при «Все валюты» суммы возвращаются отдельными строками по валютам;
- сделки без суммы считаются с `amount = 0`;
- сделки без валюты учитываются в количестве, но исключаются из денежных сумм.

KPI:

- «Открыто сейчас»: `stageSemanticId = P`, выбранная воронка, без фильтра по `createdAt`, с фильтром валюты;
- «Открыто из созданных за период»: `stageSemanticId = P`, `createdAt` внутри периода;
- «Выиграно за период»: `stageSemanticId = S`, `closedAt` внутри периода;
- «Сумма выигранных за период»: сумма `amount` по выигранным за период;
- «Средний чек»: сумма выигранных / количество выигранных, `0` при отсутствии выигранных.

## 5. API приложения

Все endpoint'ы BFF возвращают JSON. Имена endpoint'ов являются внутренним контрактом приложения и могут быть изменены до реализации, но должны сохранять описанную ответственность.

### 5.1. `GET /api/bootstrap`

Назначение:

- проверить пользовательскую сессию;
- вернуть доступные справочники для первичной отрисовки;
- выбрать значения фильтров по умолчанию.

Параметры:

- параметры не требуются, пользовательский контекст берётся из gateway/session.

Ответ:

- текущий пользователь, если доступен;
- список доступных воронок;
- выбранная по умолчанию воронка;
- доступные валюты;
- period preset по умолчанию;
- предупреждения о частично недоступных справочниках.

Ошибки:

- `401 SESSION_REQUIRED`;
- `403 BITRIX_ACCESS_DENIED`;
- `403 SCOPE_MISSING`;
- `502 VIBECODE_UNAVAILABLE`.

### 5.2. `GET /api/dashboard`

Назначение:

- вернуть все данные дашборда для активных фильтров.

Query-параметры:

- `categoryId`;
- `dateFrom`;
- `dateTo`;
- `currency`, где специальное значение `all` означает «Все валюты».

Ответ:

- KPI;
- воронка по стадиям;
- график динамики;
- последние сделки;
- предупреждения;
- meta-информация о truncation, cache и времени расчёта.

Ошибки:

- `400 INVALID_FILTERS`;
- `401 SESSION_REQUIRED`;
- `403 BITRIX_ACCESS_DENIED`;
- `403 SCOPE_MISSING`;
- `429 RATE_LIMITED`;
- `502 VIBECODE_UNAVAILABLE`.

### 5.3. `GET /api/references/stages`

Назначение:

- вернуть стадии конкретной воронки.

Query-параметры:

- `categoryId`.

Ответ:

- список стадий в справочном порядке;
- entity id справочника;
- cache metadata.

### 5.4. `GET /api/deals/recent`

Назначение:

- точечно обновить таблицу последних сделок без пересчёта всего дашборда.

Query-параметры:

- `categoryId`;
- `dateFrom`;
- `dateTo`;
- `currency`;
- `limit`, по умолчанию `15`, максимум `20`.

Ответ:

- строки таблицы последних сделок;
- предупреждение о недоступности пользователей, если имена ответственных не удалось получить.

### 5.5. `GET /api/deals`

Назначение:

- вернуть список сделок для таблицы или диагностического просмотра в рамках внутренних DTO.

Query-параметры:

- `categoryId`;
- `dateFrom`;
- `dateTo`;
- `currency`;
- `limit`;
- `cursor` или другой параметр пагинации после подтверждения фактического контракта VibeCode API.

Ответ:

- список `RecentDealRow` или расширенных deal DTO;
- pagination metadata;
- warnings.

### 5.6. Формат ошибок BFF

Ошибка должна возвращаться в едином формате:

- `code`: машинный код;
- `message`: безопасный текст для UI;
- `details`: технические детали без секретов;
- `missingScopes`: список недостающих scopes, если применимо;
- `retryable`: можно ли повторить запрос.

Внутренний enum ошибок:

- `AUTH_REQUIRED`;
- `SESSION_EXPIRED`;
- `SCOPE_DENIED`;
- `CRM_ACCESS_DENIED`;
- `RATE_LIMITED`;
- `UPSTREAM_TIMEOUT`;
- `UPSTREAM_UNAVAILABLE`;
- `DATA_TRUNCATED`;
- `VALIDATION_ERROR`;
- `UNKNOWN`.

Повтор запросов:

- frontend debounce при изменении фильтров: 400-500 мс;
- timeout для справочников: 5 секунд;
- timeout для агрегатов: 10-15 секунд;
- максимум повторов безопасного read-запроса: 2;
- backoff: 500 мс, затем 1500 мс;
- автоматически повторять только `429`, `502`, `503`, `504`;
- не повторять автоматически `400`, `401`, `403`;
- ограничить одновременные upstream-запросы числом 4.

## 6. Интеграции

### 6.1. Битрикс24

Использование:

- placement в левом меню;
- iframe lifecycle;
- CRM-права текущего пользователя;
- открытие карточки сделки по ссылке или через SDK, если контекст предоставляет такую возможность;
- локаль и форматирование дат/валют, если доступно.

Минимальные права/scopes:

- `crm` для сделок, воронок, стадий и CRM-данных;
- `user_brief` для отображения ограниченной информации об ответственных сотрудниках.

Полный scope `user` и `user_basic` не входят в MVP. `user_basic` допустим только при появлении требования показывать email или телефон.

### 6.2. VibeCode Gateway

Использование:

- передача пользовательского session token в BFF;
- обеспечение пользовательского контекста встроенного приложения;
- обработка сценариев переоткрытия или повторной авторизации при истёкшей сессии.

### 6.3. VibeCode API

Основные endpoint'ы:

- `/v1/me` — проверка ключа, пользовательского контекста и доступных возможностей;
- `/v1/guide` — контракт сущностей и полей;
- `/v1/deals` — список сделок и постраничная загрузка;
- `/v1/deals/search` — поиск сделок с фильтрами;
- `/v1/deals/aggregate` — быстрые агрегированные расчёты;
- `/v1/deal-categories` — список воронок;
- `/v1/statuses` — стадии и семантика;
- `/v1/users` — пользователи;
- `/v1/currencies` — валюты.

Перед реализацией интеграционного слоя нужно получить redacted fixtures для:

- `GET /v1/me`;
- `GET /v1/guide`;
- `GET /v1/deals`;
- `POST /v1/deals/search`;
- `POST /v1/deals/aggregate`;
- `GET /v1/deal-categories`;
- `GET /v1/statuses`;
- `GET /v1/users`;
- `GET /v1/currencies`.

На основе fixtures BFF должен описать Zod external schemas, внутренние DTO, mapper и contract-тесты. Нельзя писать интеграционный слой по предполагаемым полям API.

### 6.4. Сервер размещения

MVP размещается на Black Hole или другом согласованном сервере.

Требования:

- Node.js 20 runtime;
- HTTPS;
- безопасное хранение `VIBECODE_APP_KEY`;
- настройка CORS только для разрешённых origins;
- healthcheck endpoint `GET /health`;
- readiness endpoint `GET /ready`;
- логирование и мониторинг ошибок;
- возможность деплоя frontend и BFF как единого Black Hole приложения.

## 7. Роли пользователей и доступ

### 7.1. Руководитель отдела продаж

Основной пользователь MVP.

Возможности:

- открывает приложение из левого меню Битрикс24;
- видит агрегаты по доступным ему сделкам;
- выбирает воронку, период и валюту;
- анализирует KPI, стадии, динамику и последние сделки;
- открывает карточку сделки, если доступна ссылка и права Битрикс24 позволяют просмотр.

Ограничения:

- видит только данные, разрешённые CRM-правами Битрикс24;
- не может изменять сделки через приложение.

### 7.2. Обычный сотрудник продаж

Побочный пользователь.

Возможности:

- может открыть приложение, если оно доступно в портале;
- увидит только свои или доступные ему сделки согласно CRM-правам.

Ограничения:

- приложение не повышает права и не показывает скрытые сделки.

### 7.3. Администратор портала / интеграции

Возможности:

- устанавливает приложение;
- выдаёт scopes;
- настраивает placement;
- проверяет доступность приложения и ключей;
- выполняет диагностику с сервисным ключом `vibe_api_...`, если это явно отдельный сценарий.

Ограничения:

- админский диагностический режим не входит в пользовательский MVP;
- использование `vibe_api_...` не должно смешиваться с пользовательским дашбордом.

### 7.4. Разработчик / оператор поддержки

Возможности:

- смотрит технические логи;
- выполняет smoke-тесты API;
- проверяет `/v1/me`, справочники и scopes;
- анализирует ошибки интеграции.

Ограничения:

- не должен получать пользовательские session tokens из frontend или логов;
- не должен использовать сервисный ключ для обхода пользовательских CRM-прав в MVP.

## 8. Безопасность

- `VIBECODE_APP_KEY` хранится только на BFF.
- Пользовательский session token не передаётся в frontend и не логируется.
- Frontend обращается только к BFF приложения.
- BFF валидирует входные параметры фильтров.
- BFF не принимает произвольные endpoint'ы VibeCode API от клиента.
- Логи маскируют ключи, токены, cookies, authorization headers.
- Логи не содержат названия сделок, ФИО сотрудников, телефоны, email, полные ответы CRM, суммы отдельных сделок и query string с секретами.
- Ошибки frontend не должны раскрывать секреты или внутренние stack traces.
- Все операции к CRM в MVP должны быть read-only.
- CORS должен быть ограничен доменом приложения и допустимыми origins Битрикс24.
- Для кэша справочников допустим shared cache; для пользовательских данных кэш должен учитывать пользователя, портал и набор фильтров либо не использоваться в MVP.
- Токены нельзя передавать в URL.
- Если приложение использует cookies в iframe, cookies должны быть `Secure`, `HttpOnly`, `SameSite=None`.
- State-changing запросы, если появятся после MVP, должны использовать CSRF token или signed request.

Минимальные security headers:

```http
Content-Security-Policy:
  default-src 'self';
  frame-ancestors https://*.bitrix24.ru https://*.bitrix24.com;
  object-src 'none';
  base-uri 'self';

Referrer-Policy: strict-origin-when-cross-origin
X-Content-Type-Options: nosniff
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

Точный список `frame-ancestors` и разрешённых origins нужно подтвердить для регионов, где будет размещаться приложение.

Лицензии зависимостей:

- допустимые без отдельного согласования: `MIT`, `Apache-2.0`, `BSD-2-Clause`, `BSD-3-Clause`, `ISC`, `0BSD`;
- требуют ручной проверки: `MPL-2.0`, `LGPL`, `CC-BY`;
- не использовать без отдельного согласования: `GPL`, `AGPL`, `SSPL`, `BUSL`, `Unknown`, `Unlicensed`;
- dependency changes должны проходить license-аудит по `package.json` и lockfile.

## 9. Нефункциональные требования

Производительность:

- первичная загрузка справочников должна быть отделена от загрузки тяжёлых агрегатов;
- BFF должен использовать `/v1/deals/aggregate` для быстрых KPI и группировок;
- таблица последних сделок должна загружаться точным списочным запросом и не зависеть от усечённой агрегации;
- справочники кэшируются краткосрочно.
- рекомендуемые TTL: воронки 10 минут, стадии 10 минут, валюты 30-60 минут, пользователи 5-10 минут;
- агрегаты не кэшируются в MVP либо кэшируются на 30-60 секунд с ключом, учитывающим портал, пользователя и фильтры.

Надёжность:

- при недоступности пользователей таблица остаётся работоспособной с `assignedById`;
- при `meta.truncated=true` предупреждение применяется только к тем KPI и визуализациям, которые были рассчитаны по усечённому ответу;
- при неизвестной семантике стадии приложение показывает предупреждение и не угадывает классификацию;
- при истечении сессии пользователь получает понятное действие: переоткрыть приложение или авторизоваться заново.

Совместимость:

- приложение должно работать внутри iframe Битрикс24;
- локальный standalone/dev режим может использовать mock-данные, но не является production-сценарием;
- UI должен корректно работать при пустой выборке и при множестве валют.

Локализация:

- MVP ориентирован на русский интерфейс;
- даты и валюты форматируются с учётом локали и настроек портала, если они доступны.

## 10. Риски и меры снижения

| Риск | Влияние | Мера снижения |
| --- | --- | --- |
| Утечка `vibe_app_...` или session token во frontend | Критичный риск доступа к CRM-данным | Все вызовы VibeCode API только через BFF, секреты только в env/secret storage, маскирование логов |
| Обход CRM-прав через `vibe_api_...` | Некорректная модель доступа и утечка данных | Запрет сервисного ключа в пользовательском MVP, отдельный диагностический режим только вне UI |
| `meta.truncated=true` при выборке больше 5000 сделок | KPI могут быть неполными | Показывать предупреждение; в будущей версии добавить точный пересчёт постраничной загрузкой |
| Разные валюты в сделках | Некорректные денежные итоги | Не объединять суммы разных валют, показывать суммы по валютам |
| Отсутствует валюта у сделки | Неполные финансовые данные | Учитывать сделку в количестве, исключать из денежных сумм, показывать предупреждение |
| Отсутствует `stageSemanticId` | Ошибочная классификация выигранных/открытых сделок | Использовать fallback из `/v1/statuses`; если нет семантики, показывать предупреждение |
| Нет доступа к `/v1/users` | Нельзя показать имена ответственных | Показывать `assignedById` и предупреждение о недостающих правах |
| Отличие фактического контракта VibeCode API | Поломка маппинга и расчётов | Получить redacted fixtures, описать Zod external schemas, держать явный mapper в BFF, покрыть contract-тестами |
| Ошибки часового пояса | Неверные периоды и группировки | UI хранит календарные даты, BFF считает границы в timezone портала через date-adapter; тестировать границы дней |
| Справочники стадий отличаются между воронками | Неверная визуализация стадии | Загружать `/v1/statuses` по `entityId` выбранной воронки |
| Rate limits или нестабильность API | Ошибки загрузки дашборда | Retry только для безопасных read-запросов, user-friendly ошибки, кэш справочников |
| Несовместимая лицензия новой зависимости | Юридический или delivery-риск | Использовать license allowlist, проверять `package.json` и lockfile перед добавлением зависимости |
| Слишком подробные логи CRM-данных | Утечка персональных и коммерческих данных | Логировать только технические metadata, маскировать portal/user id, не логировать ФИО, названия сделок и суммы отдельных сделок |

## 11. Тестовая стратегия

### 11.1. Unit-тесты

Покрыть:

- расчёт периодов и границ дат;
- выбор шага группировки графика;
- классификацию сделок по `stageSemanticId` и fallback из стадий;
- расчёт KPI;
- расчёт средних чеков;
- группировку сумм по валютам;
- обработку сделок без суммы и без валюты;
- расчёт доли стадии;
- сортировку последних сделок;
- формирование warning codes.
- работу date-adapter с календарными датами, timezone портала и границами дня.

### 11.2. Contract-тесты BFF

Покрыть:

- маппинг VibeCode API deal fields во внутреннюю модель;
- Zod-валидацию внешних API fixtures;
- маппинг стадий `/v1/statuses` для `DEAL_STAGE` и `DEAL_STAGE_<categoryId>`;
- обработку `meta.truncated`;
- обработку внутренних ошибок `AUTH_REQUIRED`, `SESSION_EXPIRED`, `SCOPE_DENIED`, `CRM_ACCESS_DENIED`, `RATE_LIMITED`, `UPSTREAM_TIMEOUT`, `UPSTREAM_UNAVAILABLE`, `DATA_TRUNCATED`, `VALIDATION_ERROR`, `UNKNOWN`;
- отсутствие секретов в ответах BFF.

### 11.3. Integration-тесты

Проверить:

- `GET /api/bootstrap` возвращает справочники и defaults;
- `GET /api/dashboard` применяет фильтры воронки, периода и валюты;
- таблица последних сделок загружается отдельно от агрегатов;
- недоступность `/v1/users` не ломает дашборд;
- истёкшая сессия возвращает корректную ошибку для UI;
- BFF не вызывает write-методы CRM.
- retry выполняется только для `429`, `502`, `503`, `504` и не выполняется для `400`, `401`, `403`.

### 11.4. UI-тесты

Проверить:

- дефолтное состояние: основная доступная воронка, последние 30 дней, «Все валюты»;
- переключение периода, воронки и валюты;
- отображение KPI, графика, воронки и таблицы;
- empty state при отсутствии сделок;
- warnings при неполной агрегации и неполных финансовых данных;
- fallback ответственного на `assignedById`;
- корректное отображение нескольких валют;
- адаптивность внутри iframe.

### 11.5. E2E / acceptance-тесты

Проверить в тестовом портале Битрикс24:

- приложение открывается из левого меню;
- данные ограничены CRM-правами текущего пользователя;
- frontend не содержит ключей или session token;
- карточка сделки открывается по клику, если доступна ссылка;
- пользователь с ограниченными правами видит только доступные сделки;
- пользователь без нужных scopes получает понятное сообщение.

### 11.6. Security-тесты

Проверить:

- секреты отсутствуют в bundle frontend;
- session token не попадает в localStorage/sessionStorage;
- authorization headers не логируются;
- BFF отклоняет невалидные фильтры;
- CORS не открыт для произвольных origins;
- endpoint'ы BFF не позволяют проксировать произвольные VibeCode API запросы.
- bundle и backend-ответы не содержат `vibe_session_*`.
- security headers соответствуют спецификации.
- логи не содержат токены, ФИО, названия сделок, email, телефоны, полные CRM-ответы и суммы отдельных сделок.

### 11.7. License-тесты

Проверить:

- прямые и транзитивные зависимости имеют допустимые лицензии;
- lockfile входит в аудит;
- зависимости с `MPL-2.0`, `LGPL`, `CC-BY` вынесены на ручную проверку;
- зависимости с `GPL`, `AGPL`, `SSPL`, `BUSL`, `Unknown`, `Unlicensed` отсутствуют или имеют отдельное письменное согласование.

### 11.8. Тестовые наборы данных

Минимальные fixtures:

- redacted-ответы `/v1/me`, `/v1/guide`, `/v1/deals`, `/v1/deals/search`, `/v1/deals/aggregate`, `/v1/deal-categories`, `/v1/statuses`, `/v1/users`, `/v1/currencies`;
- пустая воронка;
- сделки только в работе;
- сделки выигранные и проигранные;
- сделки в нескольких валютах;
- сделки без суммы;
- сделки без валюты;
- сделки без `stageSemanticId`;
- воронка со стадиями с нулевым количеством сделок;
- выборка с `meta.truncated=true`;
- пользователь без доступа к `/v1/users`;
- периоды на границе месяца и года.

## 12. Критерии готовности MVP

MVP считается технически готовым, если:

1. Приложение открывается из левого меню Битрикс24.
2. Все запросы к CRM-данным идут через BFF и VibeCode API в пользовательском контексте.
3. Frontend не содержит `vibe_app_...`, `vibe_api_...` или session token.
4. Дашборд показывает только сделки, доступные текущему пользователю по CRM-правам.
5. По умолчанию выбраны основная доступная воронка, последние 30 календарных дней и «Все валюты».
6. KPI рассчитываются по правилам этой спецификации.
7. Воронка по стадиям строится по выбранной воронке, периоду и валюте.
8. График показывает созданные и выигранные сделки с корректной группировкой.
9. Таблица показывает последние созданные сделки выбранной воронки и периода.
10. Суммы разных валют не объединяются.
11. При неполной агрегации, неполных финансовых данных или недоступных пользователях отображаются предупреждения.
12. Приложение не выполняет write-операций в CRM.
13. Минимальные scopes для MVP зафиксированы как `crm,user_brief`.
14. Интеграционный слой построен на redacted fixtures, Zod external schemas, mappers и contract-тестах.
15. Даты периода рассчитывает BFF в timezone портала.

## 13. Будущие расширения

- режим «Все воронки» для общих KPI;
- фильтр по ответственному сотруднику;
- фильтр по отделу;
- точный пересчёт больших выборок через постраничную загрузку `/v1/deals`;
- короткоживущий кэш точных пользовательских агрегатов;
- переключатель «последние созданные» / «последние изменённые»;
- отдельный админский режим с `vibe_api_...`;
- переход на `user_basic` или полный `user` scope, только если появится требование показывать email, телефон или другие расширенные данные пользователя;
- расширенные финансовые правила: товарные позиции, оплаты, счета, налоги и пользовательские поля.
