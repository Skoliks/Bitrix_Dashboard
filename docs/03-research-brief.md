# Research brief перед реализацией дашборда воронки продаж

## Цель

Перед началом реализации нужно проверить внешние контракты, ограничения платформ, лицензии зависимостей, безопасность модели авторизации и готовность библиотек. Этот brief фиксирует вопросы, которые нужно исследовать, чтобы не закладывать архитектуру на непроверенных предположениях.

## Источники для исследования

- официальная документация VibeCode API;
- фактические ответы VibeCode API в тестовом портале: `/v1/me`, `/v1/guide`, `/v1/deals`, `/v1/deals/search`, `/v1/deals/aggregate`, `/v1/deal-categories`, `/v1/statuses`, `/v1/users`, `/v1/currencies`;
- документация Bitrix24 по локальным приложениям, placements, iframe lifecycle, scopes и REST/SDK;
- текущий код `dashboard-app` и `package.json`;
- лицензии npm-пакетов и их transitive dependencies;
- требования сервера размещения Black Hole или альтернативного production-хостинга.

## Вопросы для исследования

### 1. Как VibeCode Gateway передаёт пользовательский session token в BFF?

**Почему важно:** спецификация запрещает попадание session token во frontend, но нужно подтвердить фактический механизм передачи контекста встроенного приложения.

**Что проверить:**

- где именно появляется `Authorization: Bearer <USER_SESSION_TOKEN>`;
- приходит ли token в backend напрямую или сначала доступен iframe;
- есть ли подпись, nonce, installation id, portal id или другой способ валидации запуска;
- как BFF должен отличать легитимный iframe-запрос от прямого внешнего запроса.

**Решение перед реализацией:** выбрать точный протокол bootstrap/session exchange между iframe, gateway и BFF.

### 2. Какие scopes нужны фактически: `user`, `user_brief` или другой набор?

**Почему важно:** в концепте указан `user`, а шаблон `dashboard-app` упоминает `user_brief`. Неверный scope приведёт к ошибкам установки или недоступности ответственных.

**Что проверить:**

- какие scopes принимает Bitrix24 local app configuration;
- какие scopes требует VibeCode API для `/v1/users`;
- достаточно ли ограниченного профиля пользователя для имени ответственного;
- как API сообщает нехватку конкретного scope.

**Решение перед реализацией:** зафиксировать минимальный production-набор scopes и тексты ошибок для недостающих прав.

### 3. Какой фактический контракт полей сделки возвращает VibeCode API?

**Почему важно:** спецификация использует внутренние поля `amount`, `currency`, `createdAt`, `closedAt`, но текущий шаблон Bitrix24 работает с `opportunity`, `currencyId`, `begindate`, `closedate`.

**Что проверить:**

- имена, типы и nullable-статус полей сделки в `/v1/guide`;
- формат дат и часовой пояс;
- тип `amount`: number, string, decimal string;
- возможные значения `stageSemanticId`;
- наличие `categoryId`, `assignedById`, `updatedAt`.

**Решение перед реализацией:** составить таблицу маппинга внешних полей VibeCode API во внутреннюю модель `Deal`.

### 4. Какие фильтры поддерживают `/v1/deals`, `/v1/deals/search` и `/v1/deals/aggregate`?

**Почему важно:** KPI требуют разные даты и условия: открытые сейчас без периода, созданные за период по `createdAt`, выигранные по `closedAt`.

**Что проверить:**

- синтаксис фильтров по `categoryId`, `stageSemanticId`, `createdAt`, `closedAt`, `currency`;
- поддерживает ли API сочетание `OR`/`AND`;
- можно ли агрегировать суммы по валютам и стадии за один запрос;
- какие поля разрешены в group by;
- есть ли разные правила фильтрации для `/search` и `/aggregate`.

**Решение перед реализацией:** определить минимальный набор API-запросов для `GET /api/dashboard` и таблицы последних сделок.

### 5. Как на практике работает лимит `/v1/deals/aggregate` в 5000 записей?

**Почему важно:** при `meta.truncated=true` показатели могут быть предварительными, а UI должен честно маркировать такие данные.

**Что проверить:**

- считается ли лимит до или после фильтров;
- какие агрегаты становятся усечёнными;
- возвращает ли API точное `total`, `truncated`, `limit`, `processed`;
- стабилен ли порядок усечения;
- можно ли детектировать truncation отдельно по каждому запросу.

**Решение перед реализацией:** определить, где именно показывать warning и какие метрики помечать как предварительные.

### 6. Какие rate limits, timeouts и retry-рекомендации есть у VibeCode API?

**Почему важно:** дашборд может выполнять несколько запросов при каждом изменении фильтров.

**Что проверить:**

- лимиты запросов на пользователя, приложение, портал и IP;
- коды ошибок для rate limit и временной недоступности;
- есть ли `Retry-After`;
- рекомендуемые timeout значения;
- допустимы ли параллельные запросы к справочникам и агрегатам.

**Решение перед реализацией:** задать retry policy, timeout policy и debounce для фильтров.

### 7. Как VibeCode API кодирует ошибки доступа и истёкшей сессии?

**Почему важно:** UI должен различать переавторизацию, нехватку scopes, CRM access denied и временную ошибку API.

**Что проверить:**

- фактические error codes для `TOKEN_MISSING`, `INVALID_SESSION`, `BITRIX_ACCESS_DENIED`, `SCOPE_MISSING`;
- структура error response;
- есть ли список недостающих scopes;
- какие ошибки можно безопасно показать пользователю;
- какие ошибки нужно логировать только технически.

**Решение перед реализацией:** зафиксировать enum ошибок BFF и mapping во frontend-состояния.

### 8. Как правильно получать и кэшировать стадии разных воронок?

**Почему важно:** стадийная визуализация зависит от `DEAL_STAGE` и `DEAL_STAGE_<categoryId>`, а порядок и семантика могут отличаться между воронками.

**Что проверить:**

- фактический `entityId` для основной и дополнительных воронок;
- поля сортировки и цвета;
- nullable-правила для `semantics`;
- как часто меняются стадии;
- нужно ли инвалидировать кэш при смене воронки или портала.

**Решение перед реализацией:** определить cache key для стадий: portal/user/category/entityId и TTL.

### 9. Как определить часовой пояс портала и корректно считать границы периода?

**Почему важно:** дефолтный период и фильтры дат должны интерпретироваться в часовом поясе Битрикс24, а не сервера или браузера.

**Что проверить:**

- отдаёт ли VibeCode API или Bitrix24 SDK timezone портала;
- формат входных дат в VibeCode API;
- требуются ли ISO strings с offset или локальные даты портала;
- как API трактует `dateFrom` и `dateTo` на границе дня;
- что происходит на переходах месяца, года и daylight saving time.

**Решение перед реализацией:** выбрать библиотеку и единый формат дат для frontend, BFF и VibeCode-запросов.

### 10. Достаточно ли текущих frontend-библиотек для таблицы, графика, дат и воронки?

**Почему важно:** в проекте уже есть `@tanstack/vue-table`, `@unovis/vue`, `@internationalized/date`, `date-fns`, Bitrix24 UI. Нужно избежать лишних зависимостей.

**Что проверить:**

- можно ли построить требуемую funnel visualization на Unovis или лучше делать собственный компонент;
- хватает ли TanStack Table для последних сделок без тяжёлого grid-компонента;
- не конфликтуют ли `@internationalized/date` и `date-fns` по модели дат;
- поддерживают ли Bitrix24 UI компоненты нужные select/date range/filter states;
- есть ли проблемы bundle size для iframe-приложения.

**Решение перед реализацией:** утвердить список библиотек для MVP и запретить добавление новых без отдельного обоснования.

### 11. Какие лицензии у текущих и потенциальных зависимостей?

**Почему важно:** приложение будет production-интеграцией, и нельзя случайно добавить пакет с несовместимой лицензией.

**Что проверить:**

- лицензии прямых зависимостей из `dashboard-app/package.json`;
- transitive dependencies из lockfile;
- условия Bitrix24 UI, Bitrix24 SDK, Unovis, TanStack, Vue, Vite, Vitest, Zod;
- требования к attribution, NOTICE или распространению исходников;
- лицензии потенциальных новых библиотек для BFF, HTTP client, cache, logging.

**Решение перед реализацией:** создать allowlist лицензий и процедуру проверки dependency changes.

### 12. Какие требования безопасности есть у iframe-размещения Битрикс24?

**Почему важно:** приложение будет работать внутри портала и должно корректно настроить CSP, cookies, CORS и frame policies.

**Что проверить:**

- разрешённые `frame-ancestors`;
- требования к HTTPS и доменам;
- можно ли использовать cookies в iframe с `SameSite=None; Secure`;
- нужен ли CSRF-токен для запросов frontend -> BFF;
- какие origins Битрикс24 должны быть разрешены в CORS;
- допустимы ли service workers или localStorage в этом контексте.

**Решение перед реализацией:** определить security headers и способ защиты BFF endpoints от cross-site запросов.

### 13. Какие данные можно логировать и хранить в кэше?

**Почему важно:** дашборд работает с CRM-данными, именами сотрудников, суммами сделок и пользовательским контекстом.

**Что проверить:**

- можно ли логировать deal ids, user ids, portal ids;
- нужно ли маскировать суммы и названия сделок;
- допустим ли shared cache справочников между пользователями одного портала;
- можно ли кэшировать пользовательские агрегаты в MVP;
- сроки хранения логов и дампов ошибок.

**Решение перед реализацией:** зафиксировать logging policy и cache policy для справочников, агрегатов и ошибок.

### 14. Какой backend runtime и deployment model использовать для BFF?

**Почему важно:** текущий `dashboard-app` является frontend-шаблоном. Для BFF нужно выбрать runtime, packaging и способ деплоя на Black Hole или другой сервер.

**Что проверить:**

- поддерживает ли Black Hole Node.js/Bun/Deno/serverless или нужен отдельный сервер;
- можно ли деплоить frontend и BFF из одного репозитория;
- как задаются env secrets;
- как реализуются healthcheck, logs, rollback;
- какие ограничения по cold start, memory, request timeout.

**Решение перед реализацией:** выбрать production topology: единый Node.js сервис, отдельный BFF + static frontend или иной поддерживаемый вариант.

### 15. Как тестировать интеграцию без доступа к production CRM-данным?

**Почему важно:** расчёты должны быть проверены на реальных формах API, но нельзя полагаться только на production-портал.

**Что проверить:**

- есть ли тестовый портал Битрикс24;
- можно ли создать тестовые воронки, стадии, сделки и пользователей;
- можно ли получить sandbox keys `vibe_app_...` и `vibe_api_...`;
- можно ли стабильно воспроизвести ошибки scopes, access denied, expired session и truncation;
- какие fixtures можно хранить в репозитории без персональных данных.

**Решение перед реализацией:** определить test environment, smoke-test сценарии и набор обезличенных fixtures.

## Итоговые артефакты исследования

Перед реализацией нужно получить:

- таблицу внешних API-контрактов и маппинг во внутренние DTO;
- подтверждённый набор scopes;
- протокол session/bootstrap между iframe, gateway и BFF;
- список error codes и правила отображения ошибок;
- cache policy и logging policy;
- dependency/license allowlist;
- решение по backend runtime и deployment model;
- план интеграционного тестирования на тестовом портале.
