# ТЗ приложения «Дашборд воронки продаж»

## 1. Назначение

Приложение встраивается в левое меню Битрикс24 и предоставляет руководителю отдела продаж агрегированную аналитику по сделкам CRM через VibeCode API.

Основная цель — быстро оценивать:

- текущее состояние выбранной воронки продаж;
- сумму и количество открытых сделок;
- количество и сумму выигранных сделок за выбранный период;
- средний чек выигранной сделки;
- динамику созданных и выигранных сделок;
- распределение сделок по стадиям;
- последние созданные сделки и ответственных сотрудников.

Первая версия предназначена только для чтения и не изменяет сделки CRM.

## 2. Модель доступа и авторизация

Основной режим MVP — встроенное приложение Битрикс24 с ключом авторизации VibeCode `vibe_app_...`.

Ключ `vibe_app_...` нужен для размещения приложения внутри портала: в левом меню, вкладке CRM или другом placement. Запросы к данным выполняются в пользовательском контексте через пару:

- `X-Api-Key: <VIBECODE_APP_KEY>`;
- `Authorization: Bearer <USER_SESSION_TOKEN>`.

Пользовательский токен сессии не должен попадать в браузер приложения. Для MVP используется backend/BFF на стороне приложения, размещённый на Black Hole или другом сервере. Frontend обращается только к собственному BFF, а BFF уже вызывает VibeCode API.

Целевая цепочка запросов:

`Битрикс24 iframe -> VibeCode Gateway -> BFF приложения -> VibeCode API`

Приложение показывает данные в рамках CRM-прав пользователя, который открыл приложение. Само приложение не реализует отдельную ролевую модель и не обходит права Битрикс24. Если руководитель видит только сделки своего отдела, дашборд строится только по этим доступным сделкам. Если пользователь имеет доступ ко всем сделкам, дашборд может показывать общую статистику по доступному ему объёму.

Если API возвращает ошибку доступа к сделкам, стадиям, пользователям или другим необходимым сущностям, интерфейс должен явно показать пользователю, каких прав или scopes не хватает.

Минимальные scopes для MVP:

- `crm` — сделки, воронки, стадии и CRM-данные;
- `user` — отображение ответственных сотрудников.

## 3. Сервисный ключ для разработки и диагностики

Ключ `vibe_api_...` не является основной моделью доступа для пользовательского дашборда, встроенного в левое меню Битрикс24.

Допустимое применение `vibe_api_...`:

- проверка `/v1/me` агентом или разработчиком;
- диагностика доступных сущностей и scopes;
- чтение схемы и справочников до появления пользовательской сессии;
- smoke-тесты API;
- админские или фоновые задачи, которые явно выполняются от лица владельца ключа.

В пользовательском интерфейсе MVP нельзя использовать `vibe_api_...` для обхода CRM-прав текущего пользователя. Если в будущем появится отдельный админский режим с `vibe_api_...`, он должен быть явно отделён от пользовательского встроенного приложения и помечен как работающий от лица владельца ключа.

## 4. MVP

В первую версию входят:

1. Встраивание приложения в левое меню Битрикс24.
2. Авторизация через `vibe_app_...` и пользовательскую сессию.
3. Backend/BFF для вызовов VibeCode API.
4. Выбор одной воронки сделок.
5. Период анализа.
6. Фильтр валюты с режимом «Все валюты».
7. KPI-карточки.
8. Воронка по стадиям.
9. График динамики созданных и выигранных сделок.
10. Таблица последних созданных сделок.
11. Состояния загрузки, ошибки, пустых данных и предупреждения о неполной агрегации или неполных финансовых данных.

В MVP не входят:

- режим «Все воронки»;
- фильтр по ответственному сотруднику или отделу;
- собственная ролевая модель приложения поверх CRM-прав Битрикс24;
- анализ истории переходов сделок между стадиями;
- автоматическая конвертация валют;
- расчёт по товарным позициям, оплатам, счетам, налогам или пользовательским финансовым полям;
- изменение сделок CRM.

Режим «Все воронки» обязателен для будущей версии, так как он нужен руководителю для общей оценки работы отдела.

## 5. Воронки

Приложение работает с одной выбранной воронкой.

Список воронок загружается через `/v1/deal-categories`.

По умолчанию выбирается основная воронка сделок: `categoryId = 0`, если она доступна текущему пользователю через API.

Воронка сделки определяется полем `deal.categoryId`.

В будущей версии режим «Все воронки» может использоваться для общих KPI и общего списка сделок, но визуализация стадий должна оставаться привязанной к конкретной воронке, потому что у разных воронок разные наборы и порядок стадий.

## 6. Стадии и состояние сделки

Состояние сделки определяется не по названию стадии, а по системной семантике Битрикс24/VibeCode.

Для классификации конкретной сделки используется поле сделки `stageSemanticId`:

- `P` — сделка в работе;
- `S` — успешная / выигранная сделка;
- `F` — неуспешная / проигранная сделка.

Для получения названий, порядка, цвета и набора стадий используется справочник `/v1/statuses`:

- для основной воронки: `filter[entityId]=DEAL_STAGE`;
- для дополнительной воронки: `filter[entityId]=DEAL_STAGE_<categoryId>`.

У статуса используется поле `semantics`:

- `S` — успешная стадия;
- `F` — неуспешная стадия;
- `null` — стадия в работе или без финальной семантики.

Если `stageSemanticId` у сделки отсутствует, но справочник стадий содержит `semantics` для её `stageId`, приложение может использовать семантику из справочника стадий. Если семантика недоступна и там, приложение не должно угадывать состояние по названию стадии. В этом случае нужно показать предупреждение о невозможности корректно рассчитать часть показателей.

## 7. Период анализа

По умолчанию приложение показывает период «последние 30 календарных дней, включая сегодня».

Период интерпретируется в часовом поясе портала Битрикс24.

В MVP доступны:

- последние 7 дней;
- последние 30 дней;
- последние 90 дней;
- текущий месяц;
- прошлый месяц;
- произвольный диапазон дат.

В MVP используется смешанная модель дат:

- созданные сделки считаются по `createdAt`;
- выигранные сделки считаются по `closedAt` и `stageSemanticId = S`;
- средний чек выигранных сделок считается по сделкам с `closedAt` внутри выбранного периода;
- таблица последних сделок показывает сделки с `createdAt` внутри выбранного периода;
- воронка по стадиям показывает сделки с `createdAt` внутри выбранного периода.

Такой подход лучше соответствует пользовательскому смыслу показателей: «создано за период» и «закрыто/выиграно за период» отвечают на разные управленческие вопросы.

Все элементы дашборда рассчитываются после применения активных ограничений:

- CRM-права текущего пользователя;
- выбранная воронка;
- выбранный период;
- выбранная валюта, если выбран не режим «Все валюты».

Если пользователь не менял фильтры, используются значения по умолчанию: текущий пользователь, основная доступная воронка, последние 30 дней и «Все валюты».

## 8. KPI

Дашборд должен отображать следующие показатели.

### 8.1. Открыто сейчас

Текущая сумма и количество открытых сделок выбранной воронки.

Правило:

- сделки доступны текущему пользователю;
- `categoryId = выбранная воронка`;
- `stageSemanticId = P`;
- без фильтра по `createdAt`;
- фильтр валюты применяется.

Этот показатель отражает текущее состояние активной воронки, поэтому по умолчанию не ограничивается выбранным периодом. В интерфейсе нужно явно подписать, что KPI не зависит от периода.

### 8.2. Открыто из созданных за период

Сумма и количество открытых сделок, созданных в выбранном периоде.

Правило:

- сделки доступны текущему пользователю;
- `categoryId = выбранная воронка`;
- `stageSemanticId = P`;
- `createdAt` внутри выбранного периода;
- фильтр валюты применяется.

Этот показатель нужен для анализа притока новых открытых сделок за период. В интерфейсе он считается вторичным по отношению к «Открыто сейчас».

### 8.3. Выиграно за период

Количество выигранных сделок за выбранный период.

Правило:

- сделки доступны текущему пользователю;
- `categoryId = выбранная воронка`;
- `stageSemanticId = S`;
- `closedAt` внутри выбранного периода;
- фильтр валюты применяется.

### 8.4. Сумма выигранных за период

Сумма выигранных сделок за выбранный период.

Правило такое же, как для «Выиграно за период».

### 8.5. Средний чек выигранной сделки

Средний чек считается только по выигранным сделкам выбранного периода:

`сумма выигранных сделок / количество выигранных сделок`

Если выигранных сделок нет, средний чек равен нулю.

В режиме «Все валюты» средний чек показывается отдельно по каждой валюте. Суммы в разных валютах не объединяются.

## 9. Валюты и неполные финансовые данные

Сделки в разных валютах нельзя напрямую складывать в одну итоговую сумму.

Автоматическая конвертация по внешнему или текущему курсу не используется, потому что результат может не совпадать с финансовой логикой портала и историческими курсами.

В MVP используется режим:

- фильтр валюты содержит конкретные валюты и вариант «Все валюты»;
- в режиме «Все валюты» суммы показываются отдельными строками по каждой валюте;
- количество сделок можно суммировать независимо от валюты;
- денежные KPI, суммы по стадиям и суммы выигранных сделок не объединяют разные валюты.

Для первой версии используется стандартное поле сделки `amount` и поле `currency`. Товарные позиции, счета, оплаты, налоги и пользовательские финансовые поля не анализируются.

Если у сделки отсутствует сумма, она считается равной `0` и остаётся в количественных метриках.

Если у сделки отсутствует валюта, сделка остаётся в количественных метриках, но исключается из денежных сумм. Интерфейс должен показать предупреждение о неполных финансовых данных.

## 10. Воронка по стадиям

Основная визуализация показывает распределение сделок по стадиям выбранной воронки.

Выборка для MVP:

- сделки доступны текущему пользователю;
- `categoryId = выбранная воронка`;
- `createdAt` внутри выбранного периода;
- фильтр валюты применяется, если выбран не режим «Все валюты».

Показываются все стадии выбранной воронки, включая рабочие, выигранные, проигранные и стадии с нулевым количеством сделок. Это сохраняет реальную структуру процесса и порядок стадий.

Для каждой стадии отображаются:

- название стадии;
- количество сделок;
- доля от общей выборки;
- суммы сделок отдельными строками по валютам.

Доля стадии считается от общего количества сделок в выборке. Стадии с нулевым количеством сделок отображаются, но не увеличивают знаменатель.

Ширина или основная визуальная доля стадии рассчитывается по количеству сделок, а не по сумме. Это позволяет корректно показывать воронку даже при нескольких валютах.

Деньги показываются вторым слоем внутри стадии или во всплывающей детализации:

`12 сделок · RUB 1 200 000 · USD 8 500`

Если валют слишком много, интерфейс показывает основные строки и раскрытие «ещё».

Визуализация перестраивается после изменения периода, воронки или валюты.

## 11. График динамики

График показывает изменение количества сделок во времени.

Основные линии:

- созданные сделки — по `createdAt`;
- выигранные сделки — по `closedAt` и `stageSemanticId = S`.

Рекомендуемый шаг группировки:

- до 31 дня включительно — по дням;
- от 32 до 180 дней — по неделям;
- больше 180 дней — по месяцам.

Если выбран режим «Все валюты», график количества сделок не разделяется по валютам. Денежные графики в MVP не обязательны.

## 12. Таблица последних сделок

Приложение показывает 10-20 последних созданных сделок выбранной воронки и периода.

Рекомендуемое количество — 15 сделок.

Сортировка MVP:

`createdAt desc`

В таблицу попадают все сделки выбранной воронки, созданные в выбранном периоде и доступные текущему пользователю, независимо от текущего статуса сделки.

Для каждой сделки отображаются:

- название;
- сумма и валюта;
- стадия;
- ответственный;
- дата создания.

Ответственный определяется по `assignedById`. Для отображения имени используется `/v1/users`.

Если у приложения нет доступа к пользователям, интерфейс должен показать глобальное предупреждение о нехватке прав для отображения ответственных. Допустимый временный fallback — показать `assignedById` в таблице.

Для MVP допустимо открывать карточку сделки в Битрикс24 при клике по строке, если VibeCode или placement-контекст предоставляет корректную ссылку на сделку.

Будущее улучшение: добавить переключатель сортировки «последние созданные» / «последние изменённые». Режим «последние изменённые» должен использовать `updatedAt desc`.

## 13. Работа с большими выборками

Для быстрых KPI и группировок можно использовать `/v1/deals/aggregate`.

По документации VibeCode агрегатор обрабатывает максимум 5000 записей. Если подходящих записей больше, API может вернуть `meta.truncated=true`, а результат будет рассчитан по усечённой выборке.

Поведение MVP:

- использовать `/v1/deals/aggregate` для быстрых расчётов;
- проверять `meta.truncated`;
- если `meta.truncated=true`, показывать предупреждение: «Выборка больше 5000 сделок, агрегированные показатели могут быть предварительными»;
- не скрывать данные, но явно маркировать их как потенциально неполные;
- таблицу последних сделок можно загружать отдельным точным запросом к списку или поиску сделок, чтобы список последних сделок не зависел от усечённой агрегации.

Целевое поведение будущей версии:

- при `meta.truncated=true` запускать точный серверный пересчёт через постраничную загрузку `/v1/deals`;
- считать KPI и группировки на стороне приложения;
- кэшировать точный результат по набору фильтров на короткое время;
- показывать пользователю состояние «идёт точный пересчёт».

## 14. Backend/BFF и обработка данных

BFF отвечает за:

- получение пользовательского контекста от VibeCode Gateway;
- вызовы VibeCode API с `vibe_app_...` и пользовательским session token;
- хранение ключа приложения вне браузера;
- нормализацию ответов API в формат, удобный frontend;
- обработку ошибок доступа, истечения сессии и превышения лимитов;
- кэширование справочников на короткое время.

Кэширование в MVP рекомендуется для справочников, которые редко меняются:

- `/v1/deal-categories`;
- `/v1/statuses`;
- `/v1/currencies`;
- `/v1/users`.

При ошибках `TOKEN_MISSING`, `INVALID_SESSION` или аналогичных состояниях авторизации приложение должно предложить пользователю переоткрыть приложение или пройти авторизацию заново, в зависимости от сценария VibeCode Gateway.

При `BITRIX_ACCESS_DENIED` или нехватке scopes приложение должно показать понятное сообщение, какая часть данных недоступна.

## 18. API и данные

Основные endpoint'ы:

- `/v1/me` — проверка ключа, пользовательского контекста и доступных возможностей;
- `/v1/guide` — статический контракт сущностей и полей;
- `/v1/deals` — список сделок и постраничная загрузка;
- `/v1/deals/search` — поиск сделок с фильтрами;
- `/v1/deals/aggregate` — быстрые агрегированные расчёты;
- `/v1/deal-categories` — список воронок сделок;
- `/v1/statuses` — справочники стадий и их семантика;
- `/v1/users` — имена ответственных сотрудников;
- `/v1/currencies` — список валют.

Ключевые поля сделки:

- `id`;
- `title`;
- `amount`;
- `currency`;
- `categoryId`;
- `stageId`;
- `stageSemanticId`;
- `assignedById`;
- `createdAt`;
- `updatedAt`;
- `closedAt`.

Если фактический контракт API отличается от этих имён, BFF должен выполнить явный маппинг к внутренней модели приложения.

## 19. Acceptance criteria MVP

MVP считается готовым, если:

1. Приложение открывается из левого меню Битрикс24.
2. Запросы к данным выполняются через `vibe_app_...` в контексте текущего пользователя.
3. Frontend не содержит `vibe_app_...`, `vibe_api_...` или пользовательский session token.
4. Дашборд показывает только сделки, доступные текущему пользователю по CRM-правам.
5. По умолчанию выбраны основная доступная воронка, последние 30 календарных дней и «Все валюты».
6. KPI рассчитываются по правилам раздела 8.
7. Воронка по стадиям строится по сделкам, созданным в выбранном периоде, после применения активных фильтров.
8. График показывает созданные и выигранные сделки с корректной группировкой по длине периода.
9. Таблица показывает последние созданные сделки выбранной воронки и периода.
10. Суммы разных валют не объединяются.
11. При неполной агрегации пользователь видит предупреждение.
12. При сделках без валюты пользователь видит предупреждение о неполных финансовых данных.
13. При недоступности `/v1/users` пользователь видит предупреждение, а таблица может показывать `assignedById`.
14. Приложение не создаёт, не изменяет и не удаляет сделки CRM.
